# Map Population Guide — how every map gets a quality default, biggest first

> **CF ParcelMap Design Agent, 2026-10-26.** Owner ask: *"review all map modes and plan the rest of
> the game maps and scenarios; start completing all map defaults starting with the biggest maps and
> areas; a guide on how to populate all the maps with quality; how many maps are complete; can we
> generate code to populate the rest; the 100+ things that need to be written so every map can be
> populated."* This is that document. It is the operating manual for the map-population run — the
> numbers (§2), the order (§3), the buttons (§4), the quality bar (§5), and the full catalogue of
> everything a populated world needs (§6), each item marked **CODE** (generated by the pipeline) or
> **AUTHORED** (a human/agent must write it), with status and owner lane.
>
> Companions: `DEFAULT-BAKE-PLAN.md` (the original EDU bake), `MAP-MODES.md` + `BATTLE-SCENARIO-MATRIX.md`
> + `GAME-MODES-SEEDING-REVIEW.md` (modes), `MAP-QUALITY-GAP-ANALYSIS.md` (ship-quality definition),
> `MAP-MAKER-HANDOFF-RECAP.md` (what is baked vs lazy), `CONTINUOUS-WORLD-TERRAIN.md` (fields + ladder).

## 0. TL;DR

- **What "complete" means** (§1): a map is *playable* when it has a persisted DEFAULT design that
  passed the sim gate and therefore hosts the battle modes; it is *ship-quality* when it also reaches
  the MOBA-benchmark detail and carries its size-appropriate fortification and names.
- **How many are complete** (§2): of **284,284 parcels + 4,518 whole-estate maps = 288,802 map
  units**, the repo carries **366 curated maps** (14 flagship estates + 352 parcels) and the box
  registry was last baked for **EDU only (13,661, 99.6% approved, 2026-07-21)**. Everything else is
  lazy-on-first-visit. A read-only census workflow (`map-census.yml`) now prints the live truth from the
  box on demand — **run it first** (sandbox sessions cannot see `~/ef-battlefields`).
- **Can code populate the rest?** **Yes — all defaults are code.** `scripts/bake-zone.mjs ALL --estates`
  generates every parcel and every un-subdivided estate (biggest first), deterministic and idempotent,
  through the identical path the live service uses. Measured: ~55 ms/parcel, ~75–600 ms/estate, ~88 KB
  per map → the whole world is **≈4–5 h of single-core time and ≈25 GB** on the box. What code *cannot*
  do is listed as **AUTHORED** in §6 (one missing world field, ~550 fort names, new archetypes, lore pins).
- **What changed today** (shipped with this doc): whole-estate defaults with the size ladder
  (EPIC→palace, GIANT→castle, LARGE→keep) + a fallback chain so every big estate's default is
  approved; `ALL`/`--estates` bake order; batched index writes; a **zero-downtime bake** (shard +
  merge) and the **census** workflow; the lazy API serves estates too.

## 1. The completeness ladder (what "a complete map" means)

| Level | Name | Definition | Who/what produces it |
|---|---|---|---|
| **L0** | Undesigned | No registry row. First visit generates lazily (seconds). | — |
| **L1** | **Default (seed v0)** | Persisted artifact + thumbnail; deterministic from `parcelId`; windowed into the zone's world field (rivers/roads/ridges/castles continuous across parcels). | `bake-zone.mjs` or the lazy API |
| **L2** | **Playable default** | L1 **and** sim-approved (`row.approved`): every edge entry reaches the centre, corridors wide enough, safe spawns, content reachable → `meta.modes` lists the modes it hosts (DUEL/SIEGE/GUARD/CLASH/DOMINION). **This is "playable".** | same (sim gate inside `registry.save`) |
| **L3** | **Fortified / sized** | L2 **and** the size-appropriate fortification: parcels that hold a world castle carry its ring; whole-estate maps carry the ladder fort (EPIC palace / GIANT castle / LARGE keep); invest tier by size. | `estateParcel` (new) + world fields |
| **L4** | **Named & placed** | L3 **and** every fortification, town, port and landmark has a real name and lore pin (culture-consistent), hero POI parcels designated, singulars pinned. | AUTHORED (fields, names) |
| **L5** | **Ship-quality** | L4 **and** visual parity with the MOBA benchmark (`MAP-QUALITY-GAP-ANALYSIS.md` §3): lane network, jungle mass, tower chains, biome truth, budget honesty, and the engine ingests it end-to-end (stages ⑥/⑦). | generator archetype work + engine/client lanes |

**"All maps playable" = every map unit at L2.** That is entirely code. L3 is now also code for every
estate and every castle parcel. L4–L5 need the authored items in §6.

## 3. The execution plan — biggest maps and areas first

The order is **by map size, then by area**, because (a) the biggest maps are where the owner looks first
and where a flat default is most visible, (b) the biggest zones are most of the world.

| **2** | **BUS Porthaven** parcels | 70,449 | ~65 min | ~6 GB | biggest area |
| **3** | **HUB Tianxia** | 58,745 | ~55 min | ~5 GB | capital heartland, 24 EPICs |
| **4** | **ENT Mythoria** | 38,277 | ~35 min | ~3.4 GB | |
| **5** | **UW2 Blackmere** | 29,774 | ~27 min | ~2.6 GB | |
| **6** | **HS1 · HS2 · HS3 · UW3** | 44,463 | ~40 min | ~4 GB | sky tier + the vault |
| **7** | **EDU** (refresh) | 13,661 | ~12 min | — | already baked once; a re-run only fills gaps / stale seeds |
| **8** | **UW1 Ironhold — AUTHOR THE FIELD FIRST** (§6 A-9), then bake | 28,915 | ~1 h authoring + 27 min | ~2.5 GB | baking before the field exists wastes the run: every row self-heals (regenerates) the moment the field lands |

**One dispatch does phases 1–7:** `map-bake.yml` with `zones=ALL estates=true` (≈4.5 h). Because the
run is resumable and idempotent, it is equally fine to dispatch it zone by zone (`estates_only=true`,
then `BUS`, then `HUB`, …) and watch each census. **Do not include UW1 until its field is authored.**

Capacity: the full world is ≈25 GB in `~/ef-battlefields` (artifact ≈ 80 KB + thumb ≈ 8 KB per unit;
render manifests stay lazy). The census prints free disk; if the box cannot hold 25 GB, bake the
estates + BUS + HUB first (≈12 GB) and raise the disk before the rest.

## 4. How to run it (the buttons)

### 4.1 Census (read-only, any time)
GitHub → Actions → **Map registry census (read-only)** → Run. Prints disk, service state, and the
per-zone table: parcels seeded / approved / stale, estates seeded by size. Local equivalent:
`MAPS_DIR=~/ef-battlefields node scripts/registry-census.mjs [--json] [--zone=BUS]`.

### 4.2 Bake (zero-downtime)
GitHub → Actions → **Bake zone defaults (server registry)** → inputs:
- `zones` = `ALL` (every charted zone, biggest first) or e.g. `BUS HUB`
- `estates` = `true` (also bake whole-estate maps, biggest first) · `estates_only` = `true` for phase 1 alone
- `limit` = a per-zone cap for validation runs

What it does: census → bake into the **shard** `~/ef-battlefields-bake` while the service keeps serving
→ stop service → **merge** (rename parcel dirs, union the index once; owner-edited live rows always
win) → restart health-gated → census. The service is down for seconds, not hours. Re-dispatching only
fills gaps (skips rows already at GEN_VERSION).

### 4.3 Lazy path (what players hit)
`GET /internal/v1/designs/<parcel-or-estate-id>` — a committed flagship artifact wins; otherwise an
L3 parcel or an **un-subdivided estate** (new) is windowed and generated on the spot and persisted.
Baking simply moves this cost off the player's first click.

### 4.4 Local dry runs
```
MAPS_DIR=/tmp/reg node scripts/bake-zone.mjs UW3 --estates --limit=20 --flush=10
MAPS_DIR=/tmp/reg node scripts/registry-census.mjs
node scripts/merge-registry.mjs /tmp/reg /tmp/live --dry
npm test            # 7 suites incl. maps/test/estates.test.js
```

## 5. The quality bar — how to populate *with quality*

Every default passes these gates automatically; the authored work in §6 raises the ceiling.

1. **Determinism** — same `parcelId` + generator + field ⇒ byte-identical map (sentinel test in
   `maps.test.js`; estates in `estates.test.js`). Never `Math.random`/`Date.now` in the pipeline.
2. **Geometry invariants** — one entry per real edge; every edge ↔ centre ↔ edge path on walkable
   ground (validator carves a repair corridor rather than ship a sealed map); gates only ever seal
   optional shortcuts.
3. **Sim gate (hard)** — `flow.allEdgesReachCenter`, `choke.minCorridor`, `spawn.safeRadius`,
   `reach.contentOnOpenGround`, `lanes.pathable`, `barriers.optionalOnly`. Fail ⇒ stored, **not
   approved**, hosts no modes. Estates use the fallback chain so the biggest maps stay approved.
4. **Biome truth** — palette derives from the zone's biome family (desert is never green).
5. **Budget honesty** — content counts within the invest tier (estates: EPIC tier 3, GIANT/LARGE 2).
6. **Continuity** — rivers/roads/ridges cross parcel edges at the same world point (by construction
   from the field); terraform freezes edges.
7. **Fortification ladder** — EPIC palace / GIANT castle / LARGE keep / MEDIUM manor-iff-town / SMALL none.
8. **Visual proof** — the screenshot self-critique loop (`AI-MAP-AGENT-PLAYBOOK.md`): render in the
   real renderer, look, iterate. Required for every *authored* item; sampled (per-zone 40-parcel
   sample) for bakes.
9. **Approval rate as the health metric** — ≥98% approved per zone (EDU: 99.6%). A zone below that
   gets a failure census (`tools/bake_zone.mjs --validate-only`) before anything else.
10. **Owner playthrough** — the final acceptance for each zone (the EDU precedent).
